System Architecture & Hybrid Storage

How ProjectCompass is engineered below deck: the Flask application factory, 8 modular Blueprints, cooperative multiple-inheritance MRO keel, hybrid SQLite + FTS5 + ChromaDB + file-system persistence, and the RAG retrieval pipeline.

03 • Hull & Keel Design SQLite + FTS5 + ChromaDB Cooperative MRO + K8s

1. High-Level Architectural Layers

ProjectCompass combines a clean Flask Application Factory (app.py:create_app) with an inheritance-first domain engine (ProjectCompass in basefun.py) and a four-tier hybrid storage layer rooted at DATA_DIR.

2. Application Factory & Blueprint Registry

When create_app() executes in app.py, it performs a deterministic 8-step initialization sequence:

  1. Resolves DATA_DIR — Ensures writable directories exist for DATA_DIR, DATA_DIR/tmp, DATA_DIR/rag_data, Analyses/, Saved_data/, and Saved_queries/.
  2. Initializes SQLite & FTS5 — Calls models.init_db(app) and models.init_fts(app) to create all 11 relational tables and the analyses_fts virtual full-text search table with SQLite triggers.
  3. Loads Validated Settings & Feature Gates — Runs SettingsLoader.from_environment() (parsing projectcompass.yaml and PC_<SECTION>__<KEY> overrides) and installs FeatureGate(settings.features) to disable turned-off modules with clean 404 responses.
  4. Instantiates ProjectCompass — Creates the singleton webapp = ProjectCompass(dir_path=path, data_dir=data_path) stored in app.config['WEBAPP'].
  5. Bootstraps Optional Git Sync — If USE_GIT_SYNC=true and GIT_REPO_URL is configured, clones or pulls the remote Git repository into Analyses/.
  6. Registers Blueprints — Mounts all 8 blueprints (7 primary functional domains plus the dedicated remote database connections blueprint):
Blueprint Module Blueprint Name Responsibility & Key Routes
blueprints/auth.py auth_bp Session login/logout, initial /setup wizard, user management (/admin/users), API token generation, and @login_required / @role_required enforcement.
blueprints/catalog.py catalog_bp Dashboard (/), catalog search (/analysis/), create/edit/import, Structured Analysis runner (/investigations/), scomp-link Pipeline Builder (/pipeline_builder/), executions, and schedules.
blueprints/data.py data_bp SQL query workbench (/query_results/), CSV/TSV file uploader (/data_upload/), dataset listing (/data_list/), and RAWGraphs visualization bridge (/graph_analysis/).
blueprints/connections.py connections_bp Encrypted CRUD and live latency testing for remote ConnectorX databases (/connections, /connections/new, /connections/<id>/test).
blueprints/agent.py agent_bp Natural-language dataset chat (/chat, /chat/ask) using Mithril LLM generation and AST-validated safe_execute_pandas().
blueprints/rag.py rag_bp Per-analysis hybrid RAG indexing and grounded Q&A (/rag/index/<name>, /rag/ask/<name>, /chat/<name>) with prompt-injection guardrails.
blueprints/k8s.py k8s_bp Kubernetes console for k0s worker nodes (/workers) and isolated batch/v1 job runs (/runs). Flows are managed from the Analysis catalog — GET /flows redirects to /analysis; the flow editor at /flows/<name> is accessed via catalog links.
blueprints/api.py api_bp Programmatic JSON REST endpoints under /api/* for analyses, SQL queries, pipelines, executions, comments, ratings, favorites, schedules, and admin metrics.

3. Cooperative Multiple-Inheritance MRO Chain

ProjectCompass follows an inheritance-first OOP architecture where every capability is encapsulated in a dedicated Mixin/Base class and composed via Python's C3 Method Resolution Order (MRO). Every constructor accepts (dir_path, data_dir=None, **kwargs) and forwards cooperative calls via super().__init__(...): 

# Effective Method Resolution Order (ProjectCompass.__mro__)
ProjectCompass          # basefun.py          — Top-level facade, apply_settings(), create_task_config()
  ├── DataUtils         # utils/data_utils.py — DuckDB in-memory SQL + ConnectorX routing (run_sql)
  └── AnalysisUtils     # utils/analysis_utils.py — Catalog CRUD, FTS sync, Structured Analysis & Flow bridges
        └── GitSyncUtils        # utils/git_utils.py  — Automated git init/clone/pull/commit/push for Analyses/
              └── HTMLUtils     # utils/html_utils.py — header.html parser, substitute_html(), YAML env loader
                    └── K8sFlowRunnerUtils  # utils/k8s_utils.py — ConfigMap, Secret, batch/v1 Job & log watcher
                          └── K8sClusterUtils   # utils/k8s_utils.py — Node join/sync/drain/delete & token gen
                                      └── BaseK8sClient     # utils/k8s_utils.py — Kubeconfig/in-cluster API clients

4. Hybrid Storage Layer (SQLite + FTS5 + ChromaDB + Files)

Unlike early prototypes that relied solely on flat files, ProjectCompass uses a four-part hybrid storage architecture so that code artifacts remain Git-friendly on disk while metadata, search indexes, execution logs, and vector embeddings enjoy transactional speed.

4.1 Relational Database (models.py — 11 SQLAlchemy Models)

Model Class Table Name Primary Purpose & Key Columns
User users Accounts with PBKDF2/scrypt password_hash, RBAC role (admin, editor, viewer), and Bearer api_token.
AuditLog audit_log Immutable security & operational trail recording user_id, action, target, details, and ip_address.
AnalysisRecord analyses Relational mirror of catalog metadata (folder_name, title, product, owner, description, countries, is_structured, is_Flow, k8s_config).
ExecutionRun execution_runs Unified run ledger for both local structured analyses and k0s flows (analysis_name, status, inputs_json, log_text, output_path, k8s_job_name, chain_id).
Schedule schedules Cron automation definitions targeting analysis, flow with cron_expr, inputs_json, and webhook_url.
PipelineVersion pipeline_versions Versioned snapshots of visual scomp-link pipelines (analysis_name, version_num, config_json, generated_code).
DbConnection db_connections Saved remote ConnectorX database endpoints with Fernet-encrypted credentials (encrypted_credentials, db_type, read_only, managed).
Comment comments User discussion threads attached to each analysis_name (also indexed into RAG).
Rating ratings 1–5 star quality ratings per user and analysis (unique constraint on analysis_name + user_id).
Favorite favorites Per-user bookmarked analyses surfaced at the top of the catalog.

4.2 SQLite FTS5 Full-Text Index (analyses_fts)

models.init_fts(app) provisions a virtual table analyses_fts USING fts5(folder_name, title, description, product, owner, countries) coupled with three database triggers (analyses_ai, analyses_ad, analyses_au) that keep full-text search automatically synchronized on every insert, update, or delete.

5. Per-Analysis Hybrid RAG Pipeline

When a user indexes an analysis and asks a question at /chat/<analysis_name> or POST /rag/ask/<analysis_name>, the request flows through a 5-stage retrieval and guardrail pipeline: 

sequenceDiagram
  autonumber
  participant User as Operator / API
  participant Guard as RAGGuardrails
  participant Chunker as CodeAwareChunker
  participant Store as RAGStore (ChromaDB + BM25)
  participant Mithril as Mithril Server (:16180)

  Note over User,Store: Indexing Phase (POST /rag/index/{name})
  User->>Chunker: chunk_analysis(folder) + chunk_comments(name)
  Chunker-->>Store: Semantic Chunks (AST Python, SQL, YAML, MD, Comments)
  Store->>Store: Embed batches and Upsert ChromaDB

  Note over User,Mithril: Retrieval and Synthesis Phase (POST /rag/ask/{name})
  User->>Guard: Validate question (block prompt injection)
  Guard->>Store: hybrid_query(analysis_name, question, top_k=10)
  Store-->>Guard: Vector + BM25 Reciprocal Rank Fusion candidates
  Guard->>Mithril: POST /api/rerank (top_n=3)
  Mithril-->>Guard: Reranked high-precision chunks
  Guard->>Mithril: Generate grounded answer with source citations
  Mithril-->>User: Answer + cited files and lines
