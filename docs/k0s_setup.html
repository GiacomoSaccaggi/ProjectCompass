k0s Master & Worker Cluster Setup

How to provision a single-binary k0s Kubernetes flagship control plane with scripts/k0s_master_setup.sh, open required network channels, generate join tokens, attach external Linux worker vessels, and safely drain or decommission nodes.

06 • Flotilla Provisioning k0s Control Plane + Workers Zero-Dependency Binary

1. Why k0s Powers the ProjectCompass Fleet

ProjectCompass uses k0s as its recommended Kubernetes distribution because k0s ships as a single self-contained Linux binary with zero host OS package dependencies. In this topology:

  • Master Machine (Control Plane + ProjectCompass Host) — Runs the k0s control plane (`--enable-worker --no-taints`) and hosts the ProjectCompass Flask application (or schedules it in-cluster).
  • Worker Machines (External Compute Nodes) — Join the master over the network using a signed join token (`k0s worker <token>`) and execute isolated Python Flow Pods (`batch/v1` Jobs) in the kube-compass namespace.

2. Prerequisites & Firewall Port Matrix

Every machine in the cluster must run Linux (`x86_64` or `aarch64`, kernel $\ge 5.4$ recommended) with `systemd`, `curl`, and `sudo`/`root` privileges. Swap must be disabled on all nodes (`sudo swapoff -a`).

Port Protocol Direction Purpose
6443 TCP Workers / ProjectCompass → Master Kubernetes API server (`kube-apiserver`).
8132 TCP Workers → Master Konnectivity server proxy tunnel (control-plane to worker communication).
9443 TCP Workers → Master k0s controller join API endpoint.
10250 TCP Master ↔ Workers Kubelet API (used by ProjectCompass to stream `kubectl logs` from worker Pods).
4789 UDP All Nodes ↔ All Nodes Calico / Kube-Router VXLAN overlay pod-to-pod networking.
179 TCP All Nodes ↔ All Nodes BGP routing (when Kube-Router CNI is active).

3. Provisioning the k0s Master Node

Run the automated setup script scripts/k0s_master_setup.sh on your master machine. It installs `/usr/local/bin/k0s`, generates `/etc/k0s/k0s.yaml`, installs the controller with `--enable-worker --no-taints` (so single-node clusters can run Jobs immediately), waits for node readiness, creates the `kube-compass` namespace, exports a user-readable kubeconfig, and generates a worker join token: 

chmod +x scripts/k0s_master_setup.sh
sudo ./scripts/k0s_master_setup.sh \
  --namespace kube-compass \
  --kubeconfig-out "$HOME/.kube/k0s-compass.conf" \
  --token-out /etc/k0s/worker-join.token \
  --token-expiry 24h

Connecting ProjectCompass to the k0s Master

Export the generated kubeconfig before launching ProjectCompass (or configure it in .env / projectcompass.yaml): 

export KUBECONFIG="$HOME/.kube/k0s-compass.conf"
export KUBECONFIG_PATH="$HOME/.kube/k0s-compass.conf"
export K8S_NAMESPACE="kube-compass"
export K8S_DEFAULT_IMAGE="python:3.11-slim"

uv run python run.py
🧭 Captain's Log — Automatic Kubeconfig Discovery Order

BaseK8sClient._load_k8s_clients() automatically checks: (1) KUBECONFIG_PATH, (2) KUBECONFIG, (3) in-cluster ServiceAccount token (when running inside Kubernetes), (4) ~/.kube/config, and (5) /var/lib/k0s/pki/admin.conf.

4. Generating Join Tokens & Attaching Worker Nodes

Step 1: Generate a Worker Join Token on the Master

You can generate a token from the Master terminal, the Web UI (/workers), or the External CLI: 

# Option A: Directly via k0s on the master host
sudo k0s token create --role=worker --expiry=24h > /tmp/worker-join.token

# Option B: Via the ProjectCompass External CLI
uv run python scripts/compass_cli.py --url http://<MASTER_IP>:5000 --token "$PC_API_TOKEN" \
  workers token --expiry 24h

# Option C: Via the REST API
curl -X POST http://<MASTER_IP>:5000/workers/join-token \
  -H "Authorization: Bearer $PC_API_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"expiry": "24h"}'

Step 2: Install & Join k0s on Each Worker Machine

Copy `/tmp/worker-join.token` to the external Linux worker machine (or run the one-liner printed by `/workers/join-token`): 

# 1. Install the k0s binary on the worker machine
curl -sSLf https://get.k0s.sh | sudo sh

# 2. Place the join token in /etc/k0s/
sudo mkdir -p /etc/k0s
sudo mv /tmp/worker-join.token /etc/k0s/worker-join.token
sudo chmod 600 /etc/k0s/worker-join.token

# 3. Install and start the k0s worker systemd service
sudo k0s install worker --token-file /etc/k0s/worker-join.token
sudo k0s start

# 4. Verify local worker service status
sudo k0s status

Step 3: Verify & Label Workers on the Master

# List nodes from the master
sudo k0s kubectl get nodes -o wide

# Optional: Add custom node labels so Flows can target specific worker tiers via node_selector
sudo k0s kubectl label node worker-node-01 compass.io/tier=gpu workload=ml

Once joined, open http://<MASTER_IP>:5000/workers in ProjectCompass. The node will automatically appear as Ready and be persisted in the k8s_workers table.

Docker workers for local Compose deployments

The unified docker-compose.yml stack mounts the host Docker socket and a read-only worker token file into Compass. Bootstrap the stack from the project directory: 

bash scripts/k0s_setup.sh
docker compose up -d

The overlay sets PC_K0S_TOKEN_FILE and mounts the token at /run/secrets/k0s-worker.token. Alternatively, configure workers.docker.join_token_file or workers.docker.controller_container in projectcompass.yaml. The worker join address embedded in the token must be reachable from the Docker worker's network.

  • workers.docker.network: bridge is the default and supports multiple managed workers.
  • workers.docker.network: host is limited to one Compass-managed worker to avoid kubelet port collisions.
  • The overlay mounts /var/run/docker.sock; this grants host-level Docker control and should only be enabled for a trusted deployment.

The cloud-agnostic WorkerProvider reads workers.auto_provision, workers.auto_cleanup and the Docker options in projectcompass.yaml; external lifecycle scripts are also supported. Pipeline step templates are configured under connectors:. Analysis artifacts are sent through logs up to PC_ARTIFACT_INLINE_MAX_BYTES (5 MiB by default); a larger-file PC_SHARED_ARTIFACT_DIR requires a shared volume mounted in both Compass and the Job. Dataset CSVs are capped at 512 KiB per file and 800 KiB total when sent through a ConfigMap.

5. Draining, Resetting & Removing Workers

Before shutting down or upgrading a worker host, cordoning and draining ensures running Flow Pods are not abruptly terminated: 

# 1. Drain the worker via CLI (cordons the node and evicts non-DaemonSet pods)
uv run python scripts/compass_cli.py --url http://<MASTER_IP>:5000 --token "$PC_API_TOKEN" \
  workers drain --name worker-node-01

# 2. On the worker machine: stop and reset the k0s worker service
sudo k0s stop
sudo k0s reset

# 3. Remove the node from the cluster and mark it Removed in ProjectCompass
uv run python scripts/compass_cli.py --url http://<MASTER_IP>:5000 --token "$PC_API_TOKEN" \
  workers remove --name worker-node-01

6. Running Mocked & Live k0s Integration Tests

ProjectCompass includes two test suites for Kubernetes functionality: 

# 1. Fast unit & mocked K8s test suite (runs anywhere without a live cluster)
uv run pytest tests/test_k8s_integration.py -v

# 2. Live k0s cluster integration tests (creates real ConfigMaps, Secrets & batch/v1 Jobs)
KUBECONFIG="$HOME/.kube/k0s-compass.conf" uv run pytest -m k0s -v
🦑 Kraken Warning — Common Cluster Troubleshooting
  • Worker stuck in NotReady: Verify UDP port 4789 (VXLAN) and TCP ports 6443 / 8132 are open between worker and master, and inspect sudo journalctl -u k0sworker -f.
  • Single-node master Pods stay Pending: Remove the master control-plane taint via sudo k0s kubectl taint nodes --all node-role.kubernetes.io/master- || true.
  • Permission denied reading admin.conf: Never run ProjectCompass as `root` just to read `/var/lib/k0s/pki/admin.conf`; instead export a user-owned kubeconfig via sudo k0s kubeconfig admin > ~/.kube/k0s-compass.conf && chmod 600 ~/.kube/k0s-compass.conf.
