Kubernetes Console, Workers & Jobs

Operational guide to the ProjectCompass Kubernetes Flotilla Console (/workers, /runs), Dockerfile-based image builds with the local registry, isolated batch/v1 Job execution, PVC persistence, Kustomize manifests (k8s/), and security boundaries. Flows are managed from the Analysis catalog at /analysis — any analysis with compass_flow.yaml + Dockerfile is an executable flow.

07 • Regatta Dispatch batch/v1 Jobs + Chains Security & Recovery Reference

1. Kubernetes Console Overview

ProjectCompass provides three integrated views in blueprints/k8s.py backed by the 4-tier Kubernetes MRO hierarchy in utils/k8s_utils.py. Flows are no longer a separate console view — they live in the Analysis catalog (/analysis) where analyses with compass_flow.yaml + Dockerfile appear with a ⚡ Flow badge:

Console View Primary Route Core Capability
Workers Console GET /workers Reconciles live Kubernetes nodes with SQLite (`k8s_workers`), generates join tokens, and drains or removes worker nodes.
Flow Runs & Live Logs GET /runs, GET /runs/<id>/view Tracks every `batch/v1` Job execution (`ExecutionRun`) and streams real-time Pod logs over Server-Sent Events (`/runs/<id>/stream`).

2. Worker Node State Reconciliation (/workers)

Every time /workers is queried, K8sClusterUtils.k8s_sync_workers_with_db() queries `CoreV1Api.list_node()` and reconciles live cluster state with the SQLite k8s_workers table:

  • Ready — Node exists in Kubernetes and its `Ready` condition is `True`.
  • NotReady — Node exists in Kubernetes (or was pre-registered in SQLite awaiting join) and its `Ready` condition is `False` or `Unknown`.
  • Removed — Node was previously recorded as `Ready` in SQLite (`last_seen` set) and has since disappeared from the Kubernetes API, or was explicitly deleted via `DELETE /workers/<name>`.

3. Isolated Flow Execution Lifecycle (batch/v1 Jobs)

Every Kubernetes Flow run executes inside a dedicated, ephemeral Kubernetes Pod in the kube-compass namespace. Execution supports two modes: Dockerfile-based (the flow's Dockerfile is built, pushed to the local registry at registry:2 on port 5050, and launched as a K8s Job) and legacy ConfigMap injection (code and params injected via ConfigMap for backward compatibility).

Mounted Workspace & Injected Environment Variables

Inside every Flow Pod, the ConfigMap pc-flow-cfg-<run_id> is mounted read-only at /workspace:

  • /workspace/entrypoint.sh — Exports HOME=/tmp and PYTHONPATH="/tmp/.local/lib/python/site-packages:${PYTHONPATH:-}", runs pip install --user --no-cache-dir -r /workspace/requirements.txt (when non-empty), and executes exec python -u /workspace/flow.py.
  • /workspace/flow.py — The Python script saved for the Flow.
  • /workspace/params.json — Merged JSON dictionary combining Flow default parameters with run-time overrides.
  • /workspace/requirements.txt — Extra pip packages configured for the Flow.
  • Environment Variables:
    • FLOW_NAME — Name of the flow.
    • FLOW_RUN_ID — Integer ID of the ExecutionRun record.
    • FLOW_PARAMS_JSON — Raw JSON string of merged parameters.
    • FLOW_PARAMS_FILE — Always /workspace/params.json.
    • PC_PARAM_<UPPER_KEY> — Every parameter key normalized to uppercase alphanumeric characters.

4. Credentials, Secret Precedence & Resource Policy

Flows can consume credentials from existing Kubernetes Secrets or runtime inline secrets without hardcoding passwords in Python code. Secrets are attached via envFrom in the following precedence order (later sources override earlier keys):

  1. Global Default Secrets (K8S_SECRET_REFS) — Comma-separated Kubernetes Secret names configured on the Master.
  2. Flow-Level Secret References (secret_refs) — List of Kubernetes Secret names saved in the Flow's metadata.
  3. Run-Time Ephemeral Secret (pc-flow-sec-<run_id>) — Created from the secrets dict passed to POST /flows/<name>/run and automatically deleted as soon as the Job finishes.

5. Cron Scheduling

  • Unified Cron Schedules (/schedules/) — A schedule targets an executable flow from the catalog. Multi-worker Gunicorn deployments use acquire_scheduler_lock() so only the leader worker fires cron triggers.

6. Deploying ProjectCompass Inside Kubernetes (k8s/)

To run the ProjectCompass Master itself inside a Kubernetes cluster, use the Kustomize manifests in k8s/:

  • k8s/namespace.yaml — Creates the kube-compass namespace.
  • k8s/rbac.yaml — Provisions the projectcompass-sa ServiceAccount, Role, RoleBinding, and ClusterRoleBinding for node and job management.
  • k8s/pvc.yaml — Requests a 10Gi PersistentVolumeClaim (projectcompass-data-pvc) mounted at /data (DATA_DIR=/data).
  • k8s/configmap.yaml & k8s/secret.yaml — Environment configuration and secret keys.
  • k8s/deployment.yaml & k8s/service.yaml — Single-replica RWO deployment and ClusterIP service on port 5000.

7. Security Boundaries & Operational Limitations

🦑 Kraken Warning — Mandatory Production Security & Recovery Notes
  • RBAC & Code Execution Trust Boundary: Running a Flow executes arbitrary code inside the target Kubernetes namespace and can attach Secrets via `secret_refs`. The Dockerfile-based build pipeline also requires Docker socket access to build and push images to the local registry. Only grant `admin` or `editor` roles and API tokens to trusted engineers.
  • Authentication Exemptions on Legacy Routes: While /api/*, /workers, /runs, and /schedules enforce session/token authentication when users exist in SQLite, always place ProjectCompass behind a TLS reverse proxy or VPN in production and create an Admin account immediately via /setup.
  • In-Process Watcher Threads Across Master Restarts: Each Flow run spawns a daemon thread (_watch_flow_job) inside the Flask process. If the ProjectCompass Master container restarts mid-run:
    • Single-flow Jobs continue running inside Kubernetes; calling GET /runs/<id> or POST /runs/<id>/sync reconciles the final Pod status and logs from Kubernetes (`ttlSecondsAfterFinished=3600`). Note that any inline ephemeral secret `pc-flow-sec-<id>` from an interrupted watcher should be cleaned up if the master died mid-run.
  • Host-Local Scheduler Lock (`fcntl.flock`): Leader election across Gunicorn workers uses an OS file lock on `DATA_DIR/tmp/scheduler.lock`. Keep the Master Deployment at `replicas: 1` (as configured in `k8s/deployment.yaml`).
  • Git Token Persistence in `.git/config`: When `GIT_TOKEN` is used with HTTPS `GIT_REPO_URL`, `GitSyncUtils` embeds `oauth2:<token>@host` in `Analyses/.git/config`. Restrict host filesystem permissions on `DATA_DIR`.
